# Build Otto on Claude, then settle residency

PPCWay should run Otto on Anthropic's Claude models. Claude Sonnet 5.5 should be the chat agent that answers questions about an account. Claude Haiku 5.5 should handle the many small jobs behind it, and Claude Opus 5.5 should write ad text and keyword drafts, the job the Blueprint already gave to Opus. All three should be called through Google Cloud's Vertex AI in its US multi-region, with Google's Model Armor filter in Toronto in front and PPCWay's own redacted prompt log kept in Canada. On a typical small-business workload this costs about **$11.60 per customer a month, under 8% of the $149 Starter plan**. No model built for Google Ads is open to outside developers and shown to beat a general model with good tools. Every PPC competitor examined runs on general models from OpenAI, Anthropic or Google, and Google's own Ads assistant has no API. Two Google tools are still worth a look alongside Claude: the Ads API's text generator as a second source of ad drafts, if Google admits PPCWay to its closed beta, and Google's coding assistant for the engineers. Otto's accuracy depends more on the design around the model than on the model itself: typed read-only tools over the Postgres mirror, every number worked out in code, and a check that each number in a reply came from a tool. The real constraint is residency. **No current frontier model processes data in Canada, on any cloud.** The only current model with a Canadian processing commitment is Gemini 3.5 Flash in Montréal. It is older and weaker, has no announced Canadian successor, and for live chat can only be bought as reserved capacity, which Google's documents do not confirm is sold in Montréal for this model. That reserved capacity would cost roughly two to three times as much per customer as the recommended setup. The client must decide whether "data stored in Canada" means storage only, which stays true with a small change of wording, or processing too, which ties Otto to that one model at a higher cost.

## Otto's accuracy is decided by its tools more than its model

The biggest factor in whether Otto tells the truth about an account is how the data reaches the model, not which model reads it. In dbt Labs' April 2026 re-test (11 questions, each run 20 times), Claude Sonnet 4.6 scored **90.0% writing its own SQL against 98.2% when it asked for defined metrics through a semantic layer**, and GPT-5.3-Codex went from 84.1% to 100%. On questions the semantic layer did not cover, it returned an error rather than a wrong number. With text-to-SQL, in dbt's words, "failure looks like a plausible but incorrect answer" ([dbt Labs](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)). An independent paired study of 99 questions found the same pattern. Adding a short hand-written markdown description of what the metrics mean lifted accuracy from 45.5–50.5% to 67.7–68.7%, and within each condition Claude Opus 4.7, Claude Sonnet 4.6 and GPT-5.4 were statistically indistinguishable: "model choice within tier does not" explain the variance ([Rumiantsau & Fokeev](https://arxiv.org/abs/2604.25149)). Even the best text-to-SQL system on the BIRD benchmark reaches **82.95% against 92.96% for humans** ([BIRD](https://bird-bench.github.io/)). For a customer who cannot read SQL, that is roughly one wrong answer in six.

Otto should therefore work through a small set of typed, read-only tools over the Postgres mirror, not write queries itself. Example tools are `get_performance(entity, date_range, metrics)`, `compare_periods`, `top_search_terms(filter="wasted")` and `explain_change`. Shopify found that up to about 20 tools stay clear and easy to debug, that 20–50 tools blur together, and that more than 50 produce several ways to do the same thing ([Shopify Engineering](https://shopify.engineering/building-production-ready-agentic-systems)). Each tool returns figures already computed and formatted in code, each with an id. A question like "why did my cost per lead rise?" goes to a fixed calculation that splits the change into its main drivers and returns the top three. The model only puts those drivers into words. Tableau Pulse uses the same approach after finding that raw metric facts fed to a model "would often be modified incorrectly, entirely omitted, or included in a repetitive manner" ([Salesforce](https://www.salesforce.com/blog/tableau-pulse/)). A final check in the FastAPI layer pulls every number out of the draft reply and matches it against that turn's tool results. If one does not match, Otto rewrites the reply once on Opus 5.5, then falls back to a template. The design behind this check, known as proof-carrying numbers, makes the point that retrieval, citations and uncertainty estimates "improve transparency but cannot guarantee fidelity" ([Solatorio](https://arxiv.org/abs/2509.06902)). The approach also meets the requirement that every recommendation "names the data it used" ([Requirements](../Requirements.pdf)).

The same design keeps the rule that the model never calls Google Ads. Otto's only tool that leads to a change is `propose_change`. It writes a draft into the proposed-changes table and nothing more. Approval, the guardrails and the gateway do the rest. This also suits Google's own rules. The Google Ads API policies say "end users of your tool will need to manually sign in to make changes to their accounts", and prohibit "headless programmatic access to make account modifications" without Google's review of the use case or "direct, per-entity Google authentication". They also bar a hosted "MCP server, proxy endpoint, or any similar service that solely replicates, wraps, or re-exposes Google Ads programmatic capabilities", unless Google has reviewed it. Google's review for such interfaces asks for "immutable transaction logs that map every automated programmatic action directly to a verified end-advertiser account" ([Google Ads API policies](https://support.google.com/adspolicy/answer/6169371)). PPCWay's append-only action log already does that, which helps if PPCWay ever needs that review. The search-terms report needs extra care. Anyone can type instructions into Google, and if that search triggers a customer's ad, the text lands in the mirror and later in Otto's context. Prompt injection is still OWASP's number one risk for AI applications ([OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). The agreed defence is that once an agent has read untrusted text, "it must be constrained so that it is impossible for that input to trigger any consequential actions" ([Beurer-Kellner et al.](https://arxiv.org/html/2506.08837v1)). So tools mark synced text as untrusted and cut it short, Otto has no outbound channel such as fetching a web address, and the account comes from the signed-in session, enforced by Postgres row-level security, never from the model.

All of this changes what to look for in a model. Once the numbers are computed in code, the model mainly has to pick the right tool with the right arguments across several turns, follow the reply format (a sentence, then the number), start replying quickly and stay cheap. Raw reasoning power and long context matter little. In the dbt test, mid-tier Sonnet 4.6 beat flagship Opus 4.6 on semantic-layer questions. Raising GPT's reasoning effort from high to xhigh took answers from about 8 to over 20 seconds with no gain in accuracy, and for Claude, effort "changed neither results nor latency" ([dbt Labs](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)).

## Claude Sonnet 5.5 leads a three-model lineup at about $12 a customer

Claude suits Otto best for three reasons: it is the quickest capable model to start answering, it led the last independent tool-calling tests, and the product is already built around it. One caution applies to all the evidence that follows. Anthropic, OpenAI and Google each replaced their whole lineup between 2 September and 7 October 2026, so independent benchmarks for the current models are thin and some figures come from the vendors themselves ([Anthropic models overview](https://platform.claude.com/docs/en/about-claude/models/overview)).

Sonnet 5.5 costs **$2 per million input tokens and $10 per million output tokens**. Reading from the prompt cache costs $0.10 per million, cut from $0.20 on 7 October ($0.11 in Vertex's US region) ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Anthropic](https://www.anthropic.com/news/claude-haiku-5-5)). On Artificial Analysis's live measurements on 14 October, Sonnet 5.5 at low effort began answering in **about 0.7 seconds**, against about 2.9 seconds for GPT-6.1 Sol at low effort and about 25 seconds for Gemini 3.8 Flash at high. These figures move from day to day ([Artificial Analysis](https://artificialanalysis.ai/leaderboards/models)). The Berkeley function-calling leaderboard was last updated in April 2026 and only covers the previous generation. On it, Claude Opus 4.5 led at 77.47% overall and 68.38% on multi-turn tasks, while GPT-5.2 managed 55.87% overall and only 28.12% multi-turn ([BFCL](https://gorilla.cs.berkeley.edu/data_overall.csv)). On the GDPval-AA knowledge-work test that Anthropic reports, Sonnet 5.5 scored 1844 against 1487 for GPT-6 Sol, and Haiku 5.5 scored 1620 against 1437 for GPT-6 Luna ([Anthropic](https://www.anthropic.com/news/claude-sonnet-5-5); [Anthropic](https://www.anthropic.com/news/claude-haiku-5-5)). Anthropic's own footnotes say the Sonnet run used a pre-release model with a structured-output bug and that the GPT-6 Sol score may predate an OpenAI fix, so treat these as direction, not proof. On fit, the Blueprint already chose Anthropic with Opus for every writing step ([Blueprint §7.2](../docs/reference/PPCWay_Technical_Architecture_Blueprint_v1.0.pdf)). The sign-up consent text and the designed "companies that process your data" screen already name Anthropic ([settings screen](../web/components/app/settings-views.tsx)).

Cost is not what limits the choice. What could break the budget is how the system is run, not which model it uses. Without prompt caching, Sonnet chat rises from $8.14 to **$26.61** (before the 10% US-region charge). At high reasoning effort it rises to $14.44. A customer who chats three times as much costs about $30 in the US region, 20% of the Starter price ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Caching the fixed part of the prompt (Blueprint §7.3), low or medium effort by default, and the per-customer token caps already in the Blueprint keep the bill near the table. Gemini 3.8 Flash costs $0.75/$3.75 per million tokens on Google's global endpoint until 31 December 2026 ($0.825/$4.125 on regional endpoints), and twice that from 1 January 2027 ([Vertex pricing](https://cloud.google.com/vertex-ai/generative-ai/pricing)). Its cheapness is temporary, and it offers no Canadian processing either.

GPT-6.1 Sol is the serious alternative, and the case for it is real. It costs the same per token. It scored higher on Artificial Analysis's index at high effort (50 against 47) and used fewer tokens per task ($0.32 against $0.88) ([Artificial Analysis](https://artificialanalysis.ai/leaderboards/models)). The earlier GPT-6 Sol had the lowest summary-hallucination rate of any current flagship on Vectara's board, 6.5%, against 9.8–12.2% for Claude 4.x, and no Claude 5.x model has been scored there yet ([Vectara](https://github.com/vectara/hallucination-leaderboard)). Its strict output mode also accepts a `pattern` rule that could hold headlines to 30 characters as the text is written ([OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs)). Against it: its first reply is more than four times slower, it is weaker on multi-turn tool use on the last independent board, it is not offered on Google Cloud, and moving to it would mean rewriting the consent text and the list of companies that process data. The way to settle this is a one- to two-day comparison before committing. It should use about 150 real Otto questions, run against a frozen copy of the Google Ads test accounts (never the database with demo or real sign-in data), and score the right tool and date range, invented numbers, ad-text length pass rate, p50 and p95 latency, and cost per conversation. Gemini 3.5 Flash in Montréal belongs in that run, so the client can see what a Canada-only Otto costs in answer quality. A thin internal layer between PPCWay and the model provider (Blueprint §7.6) keeps a later switch to a contained piece of work.

Two details decide how well Otto handles 12 languages and Google's character limits. Smaller models lose more quality outside English. On Anthropic's own translated tests, run with extended thinking on the previous generation, Haiku 4.5 kept 95.7% of its English score in French, 94.3% in German and 92.4% in Hindi, while Sonnet 4.5 kept 97.0–98.2% in the major European languages ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/multilingual-support)). Anthropic publishes no per-language results for the 5.5 models. So customer-facing text in any language other than English should come from Sonnet, with Haiku kept to internal routing. The reply language should be set in the system prompt, and each language should be tested with about 50 Otto questions, starting with Canadian French. On character limits, Anthropic's structured outputs guarantee the JSON shape but not string length, and they only accept `minItems` of 0 or 1 ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). Google's limits are 30 characters per headline and 90 per description ([system limits](https://developers.google.com/google-ads/api/docs/best-practices/system-limits)), with 3 to 15 headlines and 2 to 4 descriptions per ad ([responsive search ads](https://developers.google.com/google-ads/api/docs/responsive-search-ads/overview)). Double-width characters, as in Chinese, Japanese or Korean, count as two ([Google Ads Help](https://support.google.com/google-ads/answer/7684791)). The Blueprint's checks written in code (§7.4) stay the real gate. They allow two rewrites with the specific fault named, then drop the asset, then fall back to a human-written template.

## No purpose-built Google Ads model beats a general model with good tools

Nothing on the market built for Google Ads should replace a general model, but two Google tools are worth a look alongside one. Google offers three kinds of AI help for Ads, and none of them can serve as Otto. Its in-product assistant, Ads Advisor, runs on "the latest Gemini models". In November 2025 Google said it would reach all English-language accounts in early December ([Google](https://blog.google/products/ads-commerce/ads-advisor-and-analytics-advisor/); [PPC Land](https://ppc.land/google-launches-ads-and-analytics-advisors-for-all-english-accounts/)). Its May 2026 successor, Ask Advisor, is "currently available in beta for English language accounts", and Google has announced no API or access for outside developers ([Google](https://blog.google/products/ads-commerce/ask-advisor/)). Google's open-source developer tools are themselves a general model plus tools. The official Google Ads MCP server is read-only and Apache-licensed. It offers a `search` tool that builds GAQL queries from structured fields, plus field metadata ([GitHub](https://github.com/googleads/google-ads-mcp)). The Developer Assistant v4 now runs inside Claude Code. It grounds itself in Google's API definitions rather than a special model, and it saves code that would change an account without ever running it ([Google Ads API docs](https://developers.google.com/google-ads/api/docs/developer-toolkit/ai-assistant)). For turning questions into GAQL, Hugging Face has only small unofficial datasets and a few community fine-tunes, none with a model card or published results. No benchmark or paper exists ([Hugging Face](https://huggingface.co/models?search=gaql)).

The competitors confirm this. Opteo's chat lets an "Orchestrator" choose the model automatically, names OpenAI, Anthropic and Gemini among its providers, and pulls account data with tool calls. A change "goes live immediately" once the user confirms ([Opteo](https://opteo.com/docs/en/articles/12968321-ai-chat)). Optmyzr's Sidekick does not say which model it uses ([Optmyzr](https://help.optmyzr.com/en/articles/8743581-optmyzr-sidekick-ai-faqs)). None of the PPC tools examined has its own ads model. PPCWay's mix of approvals, guardrails and an undo window is stricter than Opteo's confirm-and-apply, and that difference is worth saying plainly in Otto's own copy. Several competitors now offer MCP servers so their tools can be driven from Claude or ChatGPT. PPCWay should not host one that re-exposes Google Ads to outside tools. Google's API policies bar a hosted MCP server or proxy that "solely replicates, wraps, or re-exposes Google Ads programmatic capabilities" unless Google has reviewed it ([Google Ads API policies](https://support.google.com/adspolicy/answer/6169371)). The evidence on AI against human search ad copy is thin and mixed. One small 8-week test from April 2024 ran one ad of each on a $500 budget. It found a 4.98% click-through rate for human copy against 3.65% for AI copy, on older models ([Search Engine Journal](https://www.searchenginejournal.com/humans-vs-machines-ad-copy-content-test-data-study/509942/)). What improves ad drafts is the process around the model: grounding in the business's own site, character and policy checks, and feeding live asset results back in.

Fine-tuning a model on Google Ads expertise is not worth doing now. For adding knowledge, one study found that "while unsupervised fine-tuning offers some improvement, RAG consistently outperforms it" ([Ovadia et al.](https://arxiv.org/abs/2312.05934)). Google Ads facts also change too fast for trained-in knowledge to stay correct. Google shipped four major API versions, v22 to v25, between October 2025 and July 2026 ([release notes](https://developers.google.com/google-ads/api/docs/release-notes)). Otto should instead draw on a dated, curated library of Google help and policy pages and PPCWay's own playbooks. The guardrail rules belong in the instructions, not in the model's training. Fine-tuning becomes worth a look later, as a way to cut cost on the nightly batch once thousands of approved and rejected examples exist. One item belongs on the launch list. In July 2026 Google added a way for advertisers to declare ads made with outside AI tools ([Google](https://blog.google/products/ads-commerce/google-ads-ai-transparency-labels/)). The API has accepted that declaration since v25, through the `synthetic_content_info` field on ads and assets ([release notes](https://developers.google.com/google-ads/api/docs/release-notes)), so ad text Otto drafts should carry it from the start.

## Only one ageing Gemini model keeps Otto's processing inside Canada

No current frontier model can be called with a promise that the processing happens in Canada, on any cloud. On Vertex AI, which Google now calls the Gemini Enterprise Agent Platform, Toronto has no generative AI endpoint at all. In Montréal, only **Gemini 3.5 Flash, Gemini 2.5 Flash and Gemini 2.5 Pro** carry a Canadian processing tick for text, besides two older embedding models ([Data residency](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/data-residency)). The two 2.5 models retire on **20 October 2026**, six days from now, which leaves 3.5 Flash as the only one ([Model versions](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/model-versions)). Every newer Gemini (3.6, 3.7 and 3.8 Flash and 4 Argon) skipped Canada. No Claude, Mistral or open model has a Montréal tick: neither the partner-model nor the open-model residency table has a Canada column ([Locations](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/locations)). The other routes are no better. On AWS Bedrock, Claude 5.5 is reachable from Canada only through a US cross-region profile that sends requests to US regions, or through Global ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-sonnet-5-5.html)). Azure has no Canada data zone, and its pay-per-use models processed in Canada are only gpt-4o and gpt-4.1-mini ([Microsoft](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/models-sold-directly-by-azure-region-availability)). Anthropic's own API offers "us" or "global" only ([Anthropic](https://platform.claude.com/docs/en/manage-claude/data-residency)). OpenAI can store data at rest in Canada, but its Canadian "regional processing" is "None" ([OpenAI](https://developers.openai.com/api/docs/guides/your-data)).

Gemini 3.5 Flash is a Canada-only option on paper, but in practice live chat cannot simply be bought there. Google's capabilities page lists only Batch and Single Zone Provisioned Throughput as guaranteed in-region ways to use a regional endpoint outside the US and EU, and marks standard pay-per-use "Not supported" ([Supported capabilities](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/supported-capabilities)). The model's own card lists pay-per-use for the global, US and EU endpoints only. Its list of regions for reserved capacity leaves out Montréal ([Gemini 3.5 Flash card](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash)). So the overnight recommendation batch can run in Canada, at $0.825/$4.95 per million tokens. Live chat would need a reserved single-zone capacity unit, sold only through a Google account representative, and Google must first confirm it is offered for this model in Montréal ([SZPT](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/provisioned-throughput/szpt)). One unit costs about **$2,200–$2,970 a month** before any traffic, on a one-year or one-month commitment ([Pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)). It handles 675 tokens a second, with a cached input token counting as 0.1 and an output token as 6 ([Provisioned Throughput](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/provisioned-throughput/supported-models)). On the chat workload above, with peaks about four times the average, one unit covers roughly 100 customers. That puts a Canada-only Otto at **about $23–31 per customer a month**, more than twice the recommended setup. This is an estimate; the real figure depends on how bursty chat traffic turns out to be. The model is also behind the current lineup. It scores 33 on Artificial Analysis's current index at high effort, below Sonnet 5.5 at low effort (36). It takes about 17 seconds to start replying at high effort, and Artificial Analysis now labels it deprecated ([Artificial Analysis](https://artificialanalysis.ai/models/gemini-3-5-flash)). Google supports it until at least **19 May 2027**. The fair case for it is that it handles tools well. Google reports 83.6% on the MCP Atlas tool-use test, above the Claude 4.x and GPT-5.5 models it was compared with ([DeepMind](https://deepmind.google/models/model-cards/gemini-3-5-flash/)), and function calling and structured output are both guaranteed in region. Because accuracy comes mostly from the tools, a Canada-only Otto on 3.5 Flash would answer questions acceptably. It would cost more, be slower, write weaker drafts and explanations, and face a forced migration in about seven months.

Running an open model on PPCWay's own servers is the only other Canada-only route. Toronto offers L4 and H100 GPUs for Vertex model hosting ([ML locations](https://docs.cloud.google.com/gemini-enterprise-agent-platform/machine-learning/general/locations)). A single always-on L4 machine lists at about $593 a month at US-central rates ([Pricing](https://cloud.google.com/products/gemini-enterprise-agent-platform/pricing)), so one or two machines come to roughly $600–$1,700 a month before any backup capacity. That is a fixed cost large next to a per-customer bill. It would also bring a weaker model and server upkeep the owner has so far avoided.

## The client's decision is what "stored in Canada" has to mean

The landing page promises that data is stored in Canada, and the client has to decide whether that promise also covers where Otto's AI processes it. The requirements document leaves this open as "one region, or Canada, US and EU regions?" ([Requirements](../Requirements.pdf)). The product already sets a pattern for it. The designed settings screen says data lives in Canada, "Montreal and Toronto", and lists Anthropic as "Outside Canada" for "site text only" ([settings screen](../web/components/app/settings-views.tsx)). Otto will send Google Ads data to the model: campaigns, search terms and results. Whichever option is chosen, if it is not Canada-only, that row has to change.

The law allows US processing, provided PPCWay says so openly. Canada's privacy commissioner treats sending data to a processor abroad as a "use", not a disclosure, so no extra consent is needed. Organisations must still "make it plain" that information "may be processed in a foreign country" and may be reachable by that country's authorities ([OPC](https://www.priv.gc.ca/en/privacy-topics/airports-and-borders/gl_dab_090127/)). Quebec's Law 25 needs a privacy impact assessment and a written agreement before personal information leaves Quebec, even for another province ([McCarthy Tétrault](https://www.mccarthy.ca/en/insights/blogs/techlex/quebec-privacy-regulators-guide-law-25-compliant-privacy-impact-assessments)). Because PPCWay's servers are in Toronto, that assessment is needed for Quebec customers under every option. Montréal processing alone would not trigger it, since Montréal is in Quebec. The Google Ads API Terms say nothing about AI. The API policies do require apps to tell users in the app when data serves a "secondary purpose", and agencies need written client consent before "otherwise disclosing" account data ([Google Ads API policies](https://support.google.com/adspolicy/answer/6169371)). The privacy commissioner's AI principles, and the EU AI Act's Article 50 since 2 August 2026 (not delayed by the 2026 amending regulation), both expect users to be told they are talking to an AI ([OPC](https://www.priv.gc.ca/en/privacy-topics/technology/artificial-intelligence/gd_principles_ai/); [AI Act](https://artificialintelligenceact.eu/article/50/)).

| | **A. Stored in Canada, AI processed in the US (recommended)** | B. Everything in Canada | C. Each customer in their own region |
|---|---|---|---|
| Models | Claude Sonnet, Haiku and Opus 5.5 on Vertex `us` | Gemini 3.5 Flash in Montréal only, or a self-hosted open model in Toronto | Claude on Vertex `us` and `eu`; Canadian customers as in A or B |
| Quality and future | Current frontier models, with OpenAI and Google as fallbacks | One deprecated-labelled model, supported to May 2027, no successor announced | As A |
| LLM cost per customer-month | About $11.60 | About $23–31 (estimate), from reserved capacity at $2,200–2,970 a month per unit | About $11.60 |
| What the client must accept | Reworded promise and a US processor in the privacy notice | A reserved-capacity contract that Google must first confirm it sells in Montréal; slower chat, weaker drafts and a migration by mid-2027 | Separate regional databases and EU (GDPR) obligations |

**Recommendation: choose Option A, and change the wording rather than the model.** The promise would read: "Your data is stored in Canada. When you ask Otto something, the figures it needs are sent to Google Cloud in the United States to write the answer, and are not kept there or used for training." That wording extends the "Outside Canada" pattern the product already uses. It costs less than half as much per customer as Option B, needs no capacity contract, and avoids tying Otto to a model already labelled deprecated. Claude should be called through Vertex `us` rather than Anthropic's own API. Both cost 10% over global routing ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). On Vertex, though, Google is the data processor ([Anthropic](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)), and Google Cloud already hosts PPCWay. Usage is billed to the client's own Google Cloud project ([decision record](../docs/decisions/2026-10-01-both-services-run-on-cloud-run-in-toronto.md)). Google commits Haiku, Sonnet and Opus 5.5 to the US and EU multi-regions, which also covers Option C later ([Data residency](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/data-residency)). Anthropic's own pages, by contrast, give conflicting answers on how long API data is kept: one says it is not kept by default, the other that it is deleted within 30 days ([Anthropic](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention); [Anthropic Privacy Center](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)).

Option A needs six things done before launch to keep the promise true:

1. Block the global endpoint with an organisation policy, since data sent there "may be processed in any Google Cloud location around the world" ([Data residency](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/data-residency)).
2. Leave Vertex's request-response logging switched off. It is off by default, and when on it writes to PPCWay's own BigQuery table ([Zero data retention](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention)).
3. Ask the Google account team in writing whether zero data retention is possible for Claude. Google's page says that for some advanced models it "may not be possible" and to contact the account team ([Zero data retention](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention)).
4. Meet the requirement for prompt logging and policy filtering with two pieces kept in Canada:
   - Model Armor in Toronto. It screens prompts and replies for injection, sensitive data and harmful content, and stores nothing unless logging is switched on. Toronto is a "limited-support" region: it has no malicious-link filter and no multi-language detection, so French prompts need their own test ([Model Armor locations](https://docs.cloud.google.com/model-armor/locations); [features by region](https://docs.cloud.google.com/model-armor/feature-availability-by-region); [Model Armor](https://docs.cloud.google.com/model-armor/overview)).
   - PPCWay's own redacted, append-only prompt log.
5. Confirm that the Neon database sits in a Canadian region. The decision records do not say where it is, and the mirror and the prompt log will both live there.
6. Update the privacy notice and the processor list, and complete the Quebec assessment.

Option B is right only if winning customers depends on "processed in Canada", for example regulated or public-sector buyers. In that case, first get Google's written confirmation that reserved capacity for Gemini 3.5 Flash is sold in Montréal and at what price, and plan the move off 3.5 Flash now.

## Conclusion

Strict Canadian residency costs more, not less. A Canada-only Otto needs reserved capacity, roughly $23–31 per customer at launch scale against about $11.60, and Google has not confirmed it sells that capacity in Montréal for the one eligible model. It also ties Otto to a model whose support may end after May 2027, from a vendor whose last four releases all skipped Canada. That makes it a decision about how PPCWay presents itself, and one with a real price. The comparison test should run before the client decides, with Gemini 3.5 Flash included, so the trade-off is put in terms of answers Otto gets wrong rather than in the abstract. If Google later offers a newer Gemini or Claude in Montréal on pay-per-use terms, Option B becomes cheap to adopt, and the thin layer between PPCWay and the model provider is what makes that switch a small job.

The longer-term lesson is that Otto's lasting value lies in what surrounds the model. The typed tools, the number check, the guardrails, the approvals and the evaluation set built from test accounts all survive a model change. A model choice lasts only until the next release, and all three labs replaced their whole lineup in five weeks this autumn. PPCWay should therefore treat model choice as a quarterly re-run of the same test, not a one-time decision. Its position against Google's free, English-only Ask Advisor should rest on what Google does not offer: plain-language reasons, approval before anything changes, undo, and 12 languages.
